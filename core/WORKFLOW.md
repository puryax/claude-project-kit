# WORKFLOW — Claude と長期プロジェクトを完遂する進め方

> **誰が読むか: 人間と Claude の両方。** Claude には「これを読んで」と渡してよい。

**「深層」（3週間・104セッション・判断記録241件）で実際に効いたものだけを残した。**
思いつきは入れていない。**どれも一度は失敗して、その結果として決まったもの。**

---

## 0. 大前提：Claude はセッションを跨ぐと何も覚えていない

★★ **これがすべての出発点。** ★★
104 セッションのうち 103 回は「昨日までを知らない Claude」に対して始まっている。

だから必要なのは、**賢いプロンプトではなく、読めば再開できるファイル**である。
以下のすべては、この一点から導かれている。

---

## 1. ★ 着手前に「認識合わせのレベル」を聞く（A / B / C）★

**これが一番効いた1つ。**（「深層」では D-136 として制定。それ以前の D-119 を置き換えた）

| | やり方 | どんなときに |
|---|---|---|
| **A** | 合わせずにそのまま実装する | 正解が1つしかない。直し方が自明。バグ修正の大半 |
| **B** | 文字で大まかに列挙して合わせる | 選択肢が数個ある。仕様に幅がある |
| **C** | 絵コンテ・モックで細かく合わせる | ★ **見た目・手触り** ★。文字では絶対に合わない |

★ **Claude が勝手に決めないこと。** ★ 毎回、着手前に人間へ聞く。

### なぜ効くのか
**手戻りの最大の原因は「作ってから違うと分かる」こと。**
とくに **見た目は、文字でいくら詰めても合わない。**
「深層」では HUD の合意に絵で5往復かけたが、**実装は1回で通った。**
逆に絵を挟まなかった回は、実装後に4〜5回作り直している。

### ★ 見た目は人間にしか確かめられない ★
Claude はスクリーンショットを撮れても、**「かっこいいか」「気持ちいいか」は判断できない。**
数値で確かめられるもの（速さ・距離・秒数）は Claude が測る。
**それ以外は必ず人間がテストプレイする。**ここを混同すると、直したつもりで直っていない。

---

## 2. ★ docs は7ファイルに固定する ★

増やさない。減らさない。**役割が重なると、どちらが正か分からなくなる。**

| ファイル | 役割 | いつ読むか |
|---|---|---|
| `00_GDD.md` | 元の企画書。**書き換えない**（歴史として残す） | 背景を知りたいとき |
| `01_SPEC.md` | ★ **確定仕様と全数値** ★ | 実装前に該当箇所 |
| `02_ARCHITECTURE.md` | フォルダ構成・モジュール一覧・責務 | 新しいファイルを作る前 |
| `03_TASKS.md` | タスクと**完了条件**（チェックボックス） | タスク開始時 |
| `04_PROGRESS.md` | ★ **進捗記録と申し送り** ★ | **毎セッションの最初と最後** |
| `05_DECISIONS.md` | ★ **判断とその理由** ★ | 仕様に疑問を持ったとき |
| `06_TESTPLAN.md` | 手動テストの手順 | 各タスク完了時と最後 |

（必要なら `07_ASSETS.md`（素材の発注書）、`99_MANUAL.md`（人間用の操作手順）を足す）

### ★ 04_PROGRESS.md の先頭に「申し送り」を置く ★
**次のセッションの Claude が、ここだけ読めば再開できる**ようにする。
「深層」では実際に、毎回ここから始めていた。書くのは3つだけ。

- **次にやること**（1つ。複数書くと選べなくなる）
- **いまの状態**（人間の断りなく戻してはいけないもの）
- **踏んだ落とし穴**（次に同じ失敗をしないため）

### ★ 05_DECISIONS.md には「失敗の記録」も書く ★
成功した判断だけ書くと、**同じ失敗を何度も繰り返す。**
「深層」で最も価値があったのは、**間違えた仮説とその否定**だった。

書き方の型：
```
## D-NN. 何が起きたか（日付。誰の報告か）
**症状:** …
**原因:** …（★ 実測値を必ず書く ★）
**決めたこと:** …
**なぜ他の案を採らなかったか:** …
**確認:** …（数字で）
```

---

## 3. ★ 数値はすべて1つのファイルに集める ★

「深層」では `src/shared/Config.luau` に全数値を置き、**スクリプトへの直書きを禁止**した。

### なぜ効くのか
- **調整が1箇所で済む。** 人間が「もう少し速く」と言ったとき、探さなくていい
- ★ **Claude が数値を勝手に変えたかどうかが git の差分で一目で分かる** ★
- 同じ数値が2箇所にあると、**必ず片方だけ直して食い違う**

同じ考えで、**文言も1箇所**、**アセットIDも1箇所**に集める。

---

## 4. ★ 絶対ルールを CLAUDE.md に書き、破らせない ★

雛形は `CLAUDE_TEMPLATE.md`。**7つを超えないこと**（多いと守られない）。

「深層」で実際に効いたルール：

1. **数値は1つのファイルに書く。直書き禁止**
2. **仕様書にない機能を追加しない。**「良かれと思った拡張」もしない
3. **1タスクの範囲を超えて他ファイルを触らない。**「ついでに改善」禁止
4. **セッション終了時に必ず進捗記録を更新する**
5. （プロジェクト固有の、壊してはいけない一線）
6. **不明点は推測で埋めず、判断記録に疑問として書いて人間に確認する**
7. **★ 環境の状態を語る前に、その環境が生きているか検証する ★**
8. **★ 「できたはず」で報告しない。実際に動かして測ってから報告する ★**

★★ **7 と 8 が最重要。** ★★ この2つが無かった時期、Claude は
「同期が切れているのに直したつもりの報告」を何度もした。

---

## 5. ★ 不具合は「都度報告して判断を仰ぐ」★

Claude が見つけた不具合を勝手に直させない。**必ず報告 → 人間が判断 → 直す。**

### なぜか
- **その不具合が仕様かもしれない**（「深層」では実際にあった。持ち込みアイテムの扱い）
- 勝手に直すと、**1つの変更に複数の意図が混ざり、あとで切り分けられない**
- **人間が把握していない変更が積み上がる**のが、長期プロジェクトでは一番怖い

★ 例外は無い。★ 「明らかなバグ」でも報告する。

---

## 6. ★ 疑う順番を間違えない ★

「深層」で何度も起きたこと：**Claude 自身の確認スクリプトが間違っていた。**

- 遺物の効果が 0 に見えた → **効果の項目名を推測で書いていた**（ゲームは正常）
- 封鎖されていない開口部が 10 個ある → **レイを壁の内側から撃っていた**（実際は 0 個）
- 岩が勝手に変化する → **犯人は Claude 自身の別の処理だった**

★★ **「おかしい」と思ったら、まず自分の測り方を疑う。** ★★
実装を疑うのはその次。**この順番を逆にすると、直さなくていいものを壊す。**

---

## 7. ★ 検証は「外から観測できる経路」で行う ★

内部状態を覗いて「たぶん動いている」は根拠にならない。
**人間が実際に見るものと同じ経路で確かめる。**

「深層」での具体例：
- 進捗リングの表示 → 見た目は当てにならないので **移動速度が 0 でいた時間**を測った
- アニメーションが遅れる → サーバー側の値は正常だったので **画面が動き出した時刻**を測った
- 保存できているか → 変数ではなく **一度終了して開き直して**確かめた

---

## 8. ★ 完成したあとが本番 ★（2026-09-09 に追加）

「深層」は**テスト計画の全項目をパスして提出したあと**、公開版で不具合が2件出た。
どちらも **開発環境では原理的に再現しないもの**だった（通信量・通信の往復が原因）。

★★ **開発環境と本番環境で「ただ」なものが違う。** ★★
手元では 0 秒で済むもの（通信・読み込み・待ち）が、本番では 0 秒ではない。

**見た目や手触りを変えたら、本番でも一度は動かして確かめること。**

---

## 9. セッションの回し方（実際の1回の形）

```
1. 04_PROGRESS.md の申し送りを読む
2. 今日やることを1つ決める
3. ★ 認識合わせのレベルを聞く（A/B/C）★
4. 実装する
5. ★ 自分で動かして、数字で測る ★
6. 人間がテストプレイして OK を出す
7. docs を更新する（進捗・判断・完了条件のチェック）
8. ★ **今日の知見に「他のプロジェクトでも起きる」ものがあれば ClaudeKit へ還元する** ★
   進捗記録に**「ClaudeKit へ還元したこと」の欄を必ず埋める**（無ければ「なし」）。
   ★ 空欄にしないことで、忘れたことが目に見える。★
9. コミットする
```

★ **6 の前にコミットしない。** ★ 「動いたはず」でコミットすると、
どこまでが確かめ済みか分からなくなる。

---

## 10. やってはいけないこと（実際にやって痛い目を見たもの）

- ★ **人間が手で作ったものを、コードで作り直す関数を用意しない。** ★
  用意すると、いつか誰かが呼ぶ。「深層」では拠点がこれで一度壊れかけた
- **設計案（絵・モック）を資産だと思わない。** あれは使い捨て。**資料は docs だけが担う**
- **1回のコミットに複数の意図を混ぜない**
- **「ついでに」直さない**
